# Local signing certificate

Local signing is the default. `./start` generates a private development P12 certificate automatically; no signing account or certificate chain is required to run locally. For a real deployment, supply your own trusted P12 certificate and set `NEXT_PRIVATE_SIGNING_LOCAL_FILE_PATH` and, if needed, `NEXT_PRIVATE_SIGNING_PASSPHRASE` in private deployment settings. The production container configuration mounts that certificate read-only; see [docker/README.md](docker/README.md).

For development, `./start` generates a self-signed certificate under the ignored `.local/` folder. This is a local test certificate. Keep certificate files, private keys and passphrases out of Git. Use the owner's certificate for a real deployment.

Optional remote sealing uses `signature.digest.sign`: set `NEXT_PRIVATE_SIGNING_TRANSPORT=pramaan`, select `PRAMAAN_SIGNING_ACCOUNT`, and pin `PRAMAAN_SIGNING_CERTIFICATE_CHAIN` as comma-separated base64 DER public certificates, leaf first. Configure the same public certificate with the connected key on the platform. `PRAMAAN_SIGNING_ALGORITHM` supports `rsa-pkcs1-sha256` (default) and `ecdsa-sha256`; the certificate must match the algorithm. No private key is sent or stored by the template. Returned keys and signatures are verified before embedding the PDF signature. Leaving the transport as `local` keeps ordinary local sealing unchanged.

Set `PRAMAAN_SIGNING_TIMESTAMP=true` to request a trusted document timestamp through `signature.timestamp.create` after PDF sealing. The app downloads and checks the token, then embeds it as a separate incremental PDF revision that preserves the earlier signature. Tokens are retained on the platform for seven days; the embedded PDF retains its copy. Revocation and long-term validation are not supplied or claimed.

Both platform sources are switched off and not yet live-verified. Enabling a setting requests that evidence; unavailable, refused or uncertain responses stop sealing and never silently fall back to local signing or omit a requested timestamp. A member-bound connection key may need a real approver. The background sealer cannot supply that approval and stops with an explicit message; use an organisation-owned key for unattended sealing when the platform service becomes available. No approval identity is invented. Inspect active server settings in Administration → Signing settings.

Every attempt is recorded locally before sending. Completed results can be reused for an identical input; refused or uncertain attempts are not automatically repeated. Check the saved attempt and platform record before an owner-directed new sealing attempt. A rebuilt PDF with a different digest cannot reuse an earlier remote signature. Cloud certificate-secret retrieval remains unavailable; operators supply only public certificates for the remote transport. Hosted signing copies use the signature capabilities through the single client; they are separate from the local certificate flow. See [feature limitations](docs/FEATURES.md) and [architecture](ARCHITECTURE.md).

RSA-PSS sealing is refused before any remote call: the current PDF encoder labels that signature as the other RSA format and omits its required parameters. Choose a compatible key and supported algorithm explicitly; the app never substitutes one automatically.
