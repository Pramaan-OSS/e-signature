# Sign-in setup

With a key, managed sign-in is now the default. First startup provisions its server through Pramaan, registers a public HTTPS app origin, and keeps the returned addresses in private runtime state. Local development origins are allowed automatically. Managed email registration and personal-account sign-in need no client credentials. The app verifies the returned token through Pramaan before opening its own session. An email that the managed server has not verified uses the app’s existing confirmation-email flow before a session can open. Verified email, existing domain restrictions, disabled-account checks and extra verification remain enforced. An existing local email address never causes an automatic account merge; use local sign-in for that account. The organisation path below remains available. Managed provisioning, email sign-in and token verification have been checked against the free sign-in service. Other integrations use fake responses during checks.

Password sign-in and local sessions work without a connection key. Run the root setup steps in [README](../README.md), start the app, and create an account on the sign-up page. Setup creates no user account automatically. Email verification, password-reset delivery and invitations need a configured Pramaan key and a verified sender address. Do not disable those protections for a real deployment.

Personal-account and email sign-in use the managed server. Older personal/work authorization links return to the same managed sign-in screen and do not construct an external authorization URL. No separate client identifier or secret is needed.

Organisation administrators can configure one OIDC connection in Organisation settings → Organisation sign-in. Setup requires `PRAMAAN_API_KEY` and an HTTPS `NEXT_PUBLIC_WEBAPP_URL`. Register the exact callback address shown there with your issuer, then enter its client identifier and secret. Secrets are sent to Pramaan and are never returned to the page or stored locally. Choose the client authentication method your issuer supports; add exact endpoint host names only when endpoints use a different host from the issuer. Creating and removing a connection require explicit confirmation.

An existing member first signs in locally and explicitly links their organisation identity through the organisation sign-in page. Later sign-ins match the saved connection and subject identifier. Email addresses never link accounts automatically or grant membership. Removing a connection removes these links while keeping local accounts and sessions. Each sign-in attempt has an encrypted proof key, expires after ten minutes and can be redeemed once; the callback checks state and creates the existing local session.

Organisation sign-in is wired but the platform service is not deployed yet and has not been live-verified. SAML is unavailable because this connection contract supports OIDC only. The hosted challenge screen remains unavailable; server-side challenge-token verification is prepared but off by default. Password sign-in remains available. The organisation exchange has not been live-verified.
